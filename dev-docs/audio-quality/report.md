## 0. 要点（ここだけ読めば続けられる）

- 症状: スピーカーの音が「ざらざら」「びりびり」「割れている」。r1 でも USB を直した基板でも同じ
- **PSG（音源ライブラリ）を通さない素の PWM でも同じくざらざら**（T1）。原因は PSG ではない
- **GPIO10（音声のピン）が PWM で切り替わっているあいだだけ、ホワイトノイズに近い強いノイズが出る**
  - 0V 固定・3.3V 固定では出ない（T0, T12）
  - **周波数によらない**: 20kHz〜2MHz のどれでも同じくらい（T10）
  - **デューティ 50% で最大、10% / 90% で小さい**（T12）
  - 音声に繋がっていない GPIO15 で同じ PWM を出しても出ない（T11）
- 基板は **4 層で内層に全面の GND ベタ**がある（§3b）。そのため「充放電電流が GND を回り込む」説（H）は
  有力とは考えにくくなった
- **今の候補**（§4b）: ① フィルタを抜けた PWM のキャリアがアンプを飽和・誤動作させている
  ② アンプの出力が自分の入力に回り込んでいる（発振に近い状態） ③ GND / 電源の回り込み
- **2026-09-18: J6 を GND に短絡すると無音（T17）**。ノイズは信号線を通ってアンプに入っている。③ と空間結合は否定
- **2026-09-18: J6 に 10nF で「小さくなるが消えない」、470pF で変化なし**（T17b/c）。150kHz と 20kHz で減り方に差がなく、
  基本波の量に比例していない。エッジ説も弱い
- **2026-09-18: オシロ（DS100）の最初の 2 枚**（§3 の T19）。無音時（0V）でも J6 に 75mVpp のハッシュ、
  150kHz では **400mVpp 超で 150kHz にロックしない波**（計算は 0.15Vpp の三角波）。残光ありで撮ったので周期は未確定
- **【解決。2026-09-21】原因は基板ではなくファーム。** `picoruby-machine` が `SLEEP_EN0 = 0` にしていて、Ruby のタスクが
  `sleep_ms` などで待っているあいだ PWM のクロックが止まっていた。C だけのファームで再現（§3 その 5）、
  基板（フィルタ・アンプ・スピーカー）は健全。**直し方は案 B（代入を消して全 ON）**をユーザーが選択（学習用の基板なので）。
  修正版 `dist/picoruby-pico2-debug/R2P2-PICORUBY-4.0.3-PICO2-20260921-23c5e7ce` を SWD で焼いた（5000kHz では
  プローブの USB 転送エラーで失敗、`ADAPTER_SPEED=1000` で成功）。SWD で `SLEEP_EN0/1` が全 ON、タイマーと USB が動いているのを確認。
  **修正後の耳の結果（ユーザー）: `t1_pwm_square.rb` はきれい。`melody.rb`（PSG）はメロディは聞こえるが、まだノイズが乗る。**
  素の PWM の問題は解決、**PSG 経由の音に別の原因が残っている**（§6 の S1 キャリア 22.5kHz、④ クリップなどが候補）。
  次は `t9_psg_level.rb`（音量を下げるとノイズが消えるか = クリップか）と、PSG 演奏中の J6 をオシロで
- **2026-09-21 夕方: `t9_psg_level.rb` が 1 音目で止まる件は、スクリプトの待ち方の問題だった。** `speaker.playing?` は
  MML を最後まで再生しても true のまま（`MIDIBASE::MML::Player#run` が自然に終わっても `@stopped` を立てないので、
  `Speaker#playing?` = `!player.stopped?` が戻らない）。T9 は時間で待つ形に直した。`/home/t9.rb` として実機に置いてあり、
  UART のシェルから通しで動くのを確認（10 音、31 秒）。`Speaker#playing?` 自体は未修正
- **PSG が動いているあいだにフラッシュへ書くと core1 が固まる（コードと実機で確認）。**
  `picoruby-littlefs/ports/rp2040/flash_hal.c` は core0 の割り込みを止めるだけで、core1 を止めずに `flash_range_erase/program` を呼ぶ。
  PSG は core1 でフラッシュ上のコードを実行しているので、書き込みの瞬間に読めなくなって二重フォールト → ロックアップ
  （SWD で `core1 clearing lockup after double fault`）。PSG 実行中に `r2p2dev.py push` したら再現し、シェルも無応答になった。
  PSG を起こす前の push は 2 回とも成功。**「PSG のスクリプトを [実機で実行] で何度も流すと応答しなくなる」件の原因はこれ**
  （[実機で実行] は毎回 `/home/app.rb` に書く）。**同日に修正済み**（`multicore_lockout` で書き込み中 core1 を待たせる。[../upstream-issues.md](../upstream-issues.md) の 4。
  UART のシェルからは確認済み、ページの [実機で実行] での確認はユーザー待ち）
- 実機の `/home/app.rb` は `puts "app.rb: nothing to run"` に置き換えた（T9 の古い版が起動のたびに走って、シェルが出なくなっていたため。
  起動時の `Press 's'` で 's' を送って飛ばした。プローブの UART から 1 バイト送っても固まらなかった）
- **2026-09-21 夜: T9 の結果は「音量を下げてもノイズを感じる」= クリップではない。** ユーザーの判断で PSG のキャリアを先に変えた
  （S1 / S5 の改修。`psg_drv_pwm.c`、[../upstream-changes.md](../upstream-changes.md) の 11）。焼いて SWD で確認: スライス 5 は
  DIV=1.0 / TOP=1132（132kHz）、再生中 CC が動く。**耳での結果はユーザー待ち。**
  まだノイズが残るなら次は PSG の波形そのもの: ① 矩形波・鋸波は帯域制限なしで作っている（`psg.c` の `PSG_calc_sample`）ので
  22.05kHz の折り返しが必ず乗る。三角波は滑らか（12bit）で折り返しは小さい ② 出力が片側（0 〜 振幅）で、音の出入りで直流が動く（S7）
  ③ S8（エンベロープが 1 サンプルに 1 チャンネルしか進まない）。切り分けは `t22_psg_hold.rb` で J3 のパルス幅を読む
- **2026-09-21 夜その 2: PSG の鳴らしっぱなし（T22、「三角波」v15）を J6 で測った**（`tmp/ds100/J6.{BMP,CSV}`、5MS/s × 20ms）。
  ① **波形は三角波ではなく鋸波**（437Hz、1.81Vpp、倍音が偶奇とも 1/n）。`psg.c` の折り返しの式の誤り → 修正
  （[../upstream-issues.md](../upstream-issues.md) の 5） ② **基音が 438.04Hz（−8 セント、−0.5%）**。キャリア変更後、DMA を
  ソフトで張り直すたびに PWM 2 周期ぶん足踏みしていた計算と合う → DMA を 2 チャンネルの交互連鎖にした。焼いて SWD で
  2 チャンネルの残り回数が交互に 384 → 0 と減るのを確認 ③ 倍音を引いた残りは信号の −16dB（20ms の窓では、折り返し雑音と
  ②の位相の段差を分けきれない）。**鋸波・矩形波は帯域制限なしで作っているので、折り返し雑音は原理的に残る**
  （対策は PolyBLEP などの帯域制限。未着手）。修正後の耳の結果と J6 の撮り直しはユーザー待ち
- **修正後の確認（`tmp/ds100/J6-2.{BMP,CSV}`、同じ T22）: 基音 440.33Hz（計算値 440.3Hz。足踏みは消えた）、倍音は奇数次が 1/n² で並ぶ
  本物の三角波**（649 / 69 / 23 / 12 / 7 mV。理想 649 / 72 / 26 / 13 / 8）。偶数次は 2 次が −33dB、4 次が −44dB、
  倍音を引いた残りは −44dB。どちらも DS100（8bit）の直線性と量子化の限界と同じ桁なので、これ以上はこのオシロでは言えない。
  **耳では「ノイズは無いように感じる。若干ひずみは感じる」**（ユーザー）。v15 の大音量での話なので、次は T9 で音量を下げたときに
  ひずみが消えるか（アンプ・スピーカー側か）と、矩形波の折り返し雑音の残り方を聴く
- **2026-09-21 に見つけた別件 2 つ**: ① シミュレータの [実機で実行] は `/home/app.rb` に書くので、**R2P2 は起動のたびにそれを自動実行する**
  （起動ログに `Loading app.rb`）。最後に流したスクリプトが毎回の起動で走る ② 素の PWM のスクリプト（T21 / T0 / T1）を流したあと
  リセットせずに `melody.rb` を流したら**無音で、SWD で見ると core1 が二重フォールトでロックアップ**していた
  （PWM スライス 5 は T1 の最後の設定のまま EN=0、PSG は初期化されていない、ヒープの空きは 19KB）。再起動後は鳴る。
  「PSG を何度も流すと応答しなくなる」件と同じ系統の可能性。未調査
  以下の箇条書きは経緯
- **2026-09-21: T20（アンプ OFF / ON の比較）。J6 の波形はアンプの ON / OFF で変わらない。しかも大きさは
  フィルタの計算どおりだった。** これまで「計算の 3 倍」としていたのは、計算値（0.15V）が実効値に近い数字で、
  オシロの Vpp と比べていたため。正しい計算は **150kHz で約 0.34Vpp、20kHz で約 2.9Vpp、2MHz で約 2.4mVpp**（§3 の T20）。
  → 「J6 に設計より多く届いている」「アンプが J6 に何かを戻している」は**どちらも否定**。
  残るのは「**設計どおりの量のキャリアで、アンプが雑音を出す**」。0V のときのハッシュ（約 22MHz のバースト）は
  アンプ OFF でも出ていて、音とは無関係（プローブの GND リードの共振の疑い）
- **2026-09-21（その 2）: 2µs/div の CSV で、キャリアの土台（平均電圧）が数十 µs で 0.3〜0.9V 動いているのが見えた。

## 2. 音の経路（ハード）

```
GPIO10 ─[J3]─ R44 0Ω ─ R14 1kΩ ─┬─ R10 1kΩ ─┬─ R45 0Ω ─[J6]─ C24 100nF ─ R9 47kΩ ─ PAM8302A IN+
                                C22 3.3nF   C25 3.3nF                    PAM8302A IN− ─ R6 47kΩ ─ C23 100nF ─ GND
                                  GND         GND
PAM8302A: VDD = 5V（USB 由来）、SD = GPIO23（Low でミュート）、出力 → R46/R47 0Ω → LS1（8Ω 0.7W）
```

- J3 / J6 はテストポイント。**J3 は R44 より GPIO10 側**（生の PWM。R44 を外しても出ている）、
  J6 は R45 よりアンプ側（C24 の入口。R45 を外しても出ている）
- **R44 / R45（0Ω）は外して切り離すための部品**（設計者の意図）。R44 を外すとマイコンと基板上のフィルタが、
  R45 を外すとフィルタとアンプが切れる。両方外すと **J3 → ブレッドボード → J6 で外付けフィルタを組める**。
  ⚠ **0Ω は一度剥がすと戻すのが面倒**（一方通行と考える）。剥がす前に、元の経路で要る試験を全部済ませる
- **R41 / R42（68kΩ、未実装、スルーホール）はゲインを変えるための交換用**。リード抵抗が刺さる
- PAM8302A: フィルタなし D 級、ゲイン 23.5dB（データシート）、**内部発振 fOSC = 200〜300kHz（標準 250kHz）**
- RC フィルタ（1kΩ + 3.3nF の 2 段）の −3dB は約 18kHz。計算の表は plan.md §1
- 基板の設計方針書（`tmp/picorubykaigi01-board/docs/PicoBoard_design_policy.md` §4.3）は
  「10bit・146.5kHz の PWM」を前提にこのフィルタを選んでいた

### H がこれまでの結果と合う理由

- C22 は十分高い周波数では交流的にほぼショート。R14 を流れる電流は ±(1.65V 付近)/1kΩ の矩形波で、
  **大きさが周波数によらない**（T10 と合う）
- その電流の交流成分は **d×(1−d) で決まり、50% で最大**（T12 と合う）
- 0V / 3.3V 固定では電流が流れない（T0-2, T12-1/2 と合う）
- GPIO15 には負荷が無いので電流が流れない（T11-2 と合う）
- アンプの入力は IN+ 側が C24/R9、IN− 側が R6/C23 で GND に落ちている。
  **C22 / C25 の GND 電流と C23 の GND の間に電位差ができれば、それは差動入力として増幅される**
- 回り込んだ高周波は、fOSC 250kHz でスイッチングするアンプの中で可聴域に折り返され、ホワイトノイズ状になりうる
- 音を出している間は必ず PWM が切り替わるので、**どんな音にもこのノイズが乗る**（T1 のざらざら）

### H の再評価（配線を読んだあと）

内層に全面の GND ベタがある基板で、R14 を流れる ±1.7mA 程度の高周波電流が、60mm 離れたアンプ入力に
「強いノイズ」として現れるのは考えにくい。**H は候補から外さないが、有力とは見なさない。**

### B. 剥がしてから（一方通行）

**B-1. まず R45 だけ外す**（フィルタとアンプ入力が切れる。基板上のフィルタは GPIO10 に繋がったまま）

1. GPIO10 で 150kHz 50% の PWM（`t0_silence.rb`）。アンプには何も入っていない
   - **ノイズが出る** → 信号線を通らずに届いている（③、または空間的な結合）
   - **静か** → ノイズは信号線を通って入っている（① か ②）
2. **J6 に外部からきれいな音**（スマホ / PC のイヤホン出力。片チャンネルを J6、GND を GND に。
   1Vpp 程度でアンプのゲインは約 2.6 倍なので安全）。`t14_amp_only.rb` で SD を High にして聴く
   - **きれい** → アンプ・スピーカー・周辺は健全。原因は前段（①）
   - **ざらざら** → アンプ以降の問題（②、電源、スピーカー）

**B-2. 次に R44 も外す**（基板上のフィルタが完全に浮く。J3 = 生の GPIO10、J6 = アンプ入口）

- **J3 → ブレッドボード → J6 で外付けフィルタ**を組む。まず元と同じ 1kΩ + 3.3nF ×2 で、元の音が再現するか
  （B-2 以降の基準になる）
- 次に強くする: 1kΩ + 10nF ×2（−3dB 約 6kHz、150kHz で約 −40dB）、または 3 段目を足す
  - ①（キャリア）なら、フィルタを強くしただけでノイズが減る。減り方が r2 の定数決めにそのまま使える
  - 減らないなら ②/③
- 同じ配線で、PSG のキャリアを上げるソフト改修（§5-5）の効果も先に確かめられる
- GPIO10 は J3 から取る。GPIO11（ヘッダ）で代用するときは PSG のパンを右に振る必要があるので、J3 のほうが楽

**B-3. R41 / R42（ゲイン）**は、原因が決まってからの対策側で扱う

| **④** 入力過大でクリップ（T1 の「割れ」） | PSG の出力に上限（1 声 v15 矩形波は基本波約 2.1V × ゲイン 2.6 = 5.5V > 5V）。v12 程度を上限にするか `Board` の既定音量を下げる。「左に振って +3dB」は逆方向なので外す | R41/R42（ゲイン上げ）は**付けない** | 入力を分圧で下げる |

- ① と ④ はソフトと定数で今の基板でも改善できる。② と ③ は r2 の配線が本筋で、今の基板ではビーズ程度
- どの候補でも、PSG の PWM が無音時 0V で音が片側だけに振れる作り（S7）はポップ音の原因。直流の中心を真ん中に置く改修は別途価値がある

## 6. 途中で見つかった別件（音のざらざらとは別。直す価値あり）

| | 内容 | 確かさ | 場所 |
|---|---|---|---|
| S4 | `Board.default_speaker_backend` の「チャンネル 0〜2 を左に振る」設定は `:default` の音源に送っているが、`Speaker` の音は `:mml` の音源で来るので効いていない。実際は中央パン（1 声 v15 で PWM の 50%）。r1-board.md の「71%」は誤り | コードで確認、実機未確認（`t8_psg_pan.rb` で確かめられる） | `lib/picorubykaigi01/board.rb:75-79`、`mrbgems/picoruby-psg/mrblib/synth.rb` の `state_for` |
| S5 | DMA 版の PWM 分周比は SDK が小数部を 4bit に切り捨てる（1.6608 → 1.625）。実際の再生は約 22,536Hz で、合成側の 22,050Hz より約 2.2% 速い → 約 38 セント高い | 切り捨てはコードで確認、音程は未測定 | `mrbgems/picoruby-psg/ports/rp2040/psg_drv_pwm.c:72`、pico-sdk `pwm_set_clkdiv` |
| S1 | PSG の PWM キャリアが 22.5kHz で、基板フィルタの設計前提（146.5kHz）と合わない。改修案: 比較値の上限を 1132 にして 1 サンプルを DMA で 6 回書く（約 132kHz、約 22,065Hz で S5 も解消） | コードと計算 | 同上。**upstream の gem なので編集前にユーザーに確認** |

| S8 | `update_envelope` がループ途中の `return` で、1 サンプルに 1 チャンネルしかエンベロープが進まない | コードで確認 | `mrbgems/picoruby-psg/ports/common/psg.c:286-306` |
