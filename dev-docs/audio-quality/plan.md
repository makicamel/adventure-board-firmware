# スピーカーの音が汚い — 原因の切り分け計画

r1 と USB を直した基板で、`melody.rb` の音が「ざらざら」している。
ハードかソフトかを切り分ける。**ソフトで試せることから先にやる。**

調べたのは 2026-09-14。以下で「コードから」とあるものは読んだだけで、実機では未確認。

---

## 1. 音の経路

```
PSG（core1 で合成、22.05kHz 想定）
  → DMA で PWM の比較値を 1 サンプルごとに書き換え（GPIO10 = PWM5A、12bit）
  → R44 0Ω → [J3 テストポイント: 生の PWM]
  → R14 1kΩ ─┬─ R10 1kΩ ─┬─ R45 0Ω → [J6 テストポイント: フィルタ後]
             C22 3.3nF    C25 3.3nF
  → C24 100nF（直流カット）→ R9 47kΩ → PAM8302A IN+（IN− は R6 47kΩ + C23 100nF で GND）
  → R46/R47 0Ω → スピーカー LS1（8Ω 0.7W）
  PAM8302A の SD = GPIO23（Low でミュート）、電源は 5V（USB）
```

### RC フィルタの効き（計算）

1kΩ + 3.3nF の 2 段（2 段目が 1 段目に負荷として効く形）。−3dB は約 **18kHz**。

| 周波数 | 減衰 | |
|---|---|---|
| 1kHz | 0.0dB | |
| 10kHz | −1.2dB | |
| **22.5kHz** | **−4.1dB** | **今の PWM キャリア** |
| 36.6kHz | −7.3dB | DMA を使わないビルドのキャリア |
| 146.5kHz | −21.8dB | 設計方針書（`PicoBoard_design_policy.md` §4.3）が前提にした 10bit のキャリア |

C24/R9 の直流カットは約 34Hz から下を落とすだけで、音域には効かない。

## 2. 考えられる原因

### ソフト側

| # | 原因の候補 | 根拠 | 確かさ |
|---|---|---|---|
| **S1** | **PWM のキャリアが 22.5kHz しかなく、フィルタでほとんど落ちずにアンプへ入る** | `psg_drv_pwm.c:69-72`: 比較値の上限 4095（12bit）、分周比を「サンプリング周波数 × 4096」に合わせている。1 サンプル = PWM 1 周期。上の表で −4.1dB | コードで確認 |
| **S2** | **折り返し雑音**（サンプリング周波数の半分 11kHz を超える成分が、音程と無関係な低い音に化ける） | 矩形波・のこぎり波をそのまま 0/4095 で作っていて、帯域を制限していない（`common/psg.c:389-413`）。高い音ほど目立つはず | コードで確認 |
| S3 | 2 声以上でソフトクリップに当たる | `soft_clip` は 3600 を超えると急に傾きが変わる。中央パン・v15 で 2 声 4096→3659、3 声 6144→3899 | コードで確認。`melody.rb` は 1 声なので主因ではなさそう |
| S4 | 「左に振って +3dB」の設定が効いていない（音量が記録より低い） | `board.rb:75-79` は `:default` の音源に CC10 を送るが、`Speaker` の音は `:mml` の音源で来る（`synth.rb` は `[音源, チャンネル]` ごとに設定を持つ）。実際は中央パンで 1 声 v15 = 2048/4095（50%）。r1-board.md の「71%」は誤り | コードで確認。音質ではなく音量の問題 |
| S5 | 音程が約 38 セント高い | DMA 版の分周比は SDK が小数部を 4bit に切り捨てる（1.6608 → 1.625）ので、実際は約 22,536Hz で再生される。合成側は 22,050Hz のつもり | 切り捨てはコードで確認。音程のずれは未測定 |
| S6 | 合成が間に合わず、途切れてプツプツする | core1 が 64 サンプル（約 2.8ms）ずつ作る。間に合わないと直前の値のまま止まる（調査の報告） | 未確認。Ruby 側が忙しいときに出るか |
| S7 | 鳴り始め・止めるときのポップ音 | 無音時の PWM は 0（0V）で、音は 0〜振幅の片側だけ。`play_mml` のたびに SD を Low→High にする（調査の報告） | 未確認。「ざらざら」より「プツッ」の原因 |
| S8 | エンベロープが 1 チャンネル分しか進まない | `update_envelope` がループの途中で `return` している | コードで確認。エンベロープを使う音色だけ |

### ハード側

| # | 原因の候補 | 確かめ方 |
|---|---|---|
| H1 | フィルタが今のキャリアに対して弱すぎる（S1 の裏返し） | J6 をオシロで見て 22.5kHz がどれだけ残っているか。C22/C25 を大きくすれば落ちる |
| H2 | アンプの入力が大きすぎてクリップ | スピーカー端子をオシロで見る。音量（v）を下げて改善するか |
| H3 | 5V の電源ノイズ（LED ドライバの PWM、USB 電源） | LED マトリクスを消した状態と全点灯で音を比べる（ソフトで試せる） |
| H4 | スピーカーや基板のビビり（機械的な共振） | 純音を低い音から高い音まで鳴らして、特定の高さでだけ汚くなるか |
| H5 | スピーカー自体の歪み（小型・0.7W） | 別のスピーカーをつなぐ |

## 3. 検証の手順

### 段階 1: ソフトだけ、ファームは今のまま（明日の最初）

どれも短いスクリプトを基板に送って、耳で比べる。できればスマホで録音して
スペクトルを見る（無料の周波数分析アプリで十分）。
**段階 1 の各テストの前に `r2p2dev.py reset` する。**
PSG が一度 PWM を掴むと、`picoruby-pwm` の T1 と取り合いになるため。

| テスト | 内容 | 目的 |
|---|---|---|
| **T1** | **`picoruby-pwm` で素の矩形波**を GPIO10 に出す（`PWM.new(10, frequency: 262/440/880, duty: 50)`、SD を High）。PSG を通さない | **基準。** PWM のキャリアも折り返しも無い、ハードだけの音。※ 0〜3.3V いっぱいに振るので PSG の 1 声（中央パンで約半分）より大きい。T1 だけ歪むならアンプのクリップ（H2）を疑う |
| **T2** | PSG で同じ高さの矩形波を 1 声（v15、v10） | T1 と比べる。PSG を通したときだけ汚いなら S1/S2 |
| **T3** | PSG で同じ高さの三角波 | 折り返しがほとんど無い波形。三角波でも汚いなら S1（キャリア）が濃厚 |
| T4 | PSG の矩形波で高い音階（o6〜o7） | 高い音ほど音程と無関係な音が混じるなら S2 |
| T5 | T2 を、LED マトリクス消灯と全点灯で比べる | H3（電源ノイズ） |
| T6 | 2 声・3 声の和音を v15 と v10 で | S3（クリップ） |
| T7 | T1 の周波数を 100Hz〜2kHz でゆっくり上げる | H4（共振）。特定の高さだけビビるか |

#### スクリプト（`scripts/`）

| ファイル | テスト | 起動直後に流す |
|---|---|---|
| `t1_pwm_square.rb` | T1: 素の矩形波 262 / 440 / 880Hz を 3 秒ずつ | **要**（PSG を使う前） |
| `t7_pwm_sweep.rb` | T7: 素の矩形波 100Hz→2kHz を半音ずつ | **要** |
| `t2_t3_psg_tone.rb` | T2 矩形波 / T3 三角波 × v15 / v10、同じ 3 つの高さ | |
| `t4_psg_high.rb` | T4: o6〜o7 の音階を矩形波→三角波 | |
| `t5_psg_led.rb` | T5: 三角波 440Hz を LED 消灯→市松点灯→消灯 | |
| `t6_psg_chord.rb` | T6: 2 声→3 声を v15、休み、v10 | |
| `t8_psg_pan.rb` | T8（S4）: パン指定なし→p8→p0。p0 が約 3dB 大きいはず | |

どれも区切りごとに `puts` で今鳴らしているものを出す。

**流し方（USB が生きている基板）**: シミュレータのページ（`rake sim:server` → `/sim/`）で
[実機に接続] し、スクリプトをエディタに貼って [実機で実行]。出力欄で実況を見ながら聴ける。

**流し方（r1、プローブの UART）**:

```console
export R2P2_PORT=/dev/ttyACM0
tools/r2p2dev.py push dev-docs/audio-quality/scripts/t1_pwm_square.rb /home/devtest/t1.rb
tools/r2p2dev.py run --wait 20 /home/devtest/t1.rb
```

**順番**: `t1` → `t7`（ここまで PSG を使わない）→ リセット → `t2_t3` → `t4` → `t8` → `t6` → `t5`。
何度も流すと応答しなくなることがある（sim/README.md の未解決の件）ので、固まったらリセット。

#### 判定の目安

| 結果 | 疑わしいもの |
|---|---|
| T1 もきれいでない | **ハード**（H2〜H5）。段階 4 へ |
| T1 はきれい、T2 は汚い、T3 はきれい | **S2（折り返し）** |
| T1 はきれい、T2 も T3 も汚い | **S1（キャリア）** |
| T5 で明るさによって変わる | **H3（電源ノイズ）** |
| T6 で v10 なら和音もきれい | **S3（クリップ）** |

### 段階 2: ビルドの設定だけ変える（コードは変えない）

`PICORUBY_PSG_PWM_DMA=0` でビルドすると、キャリアが約 36.6kHz になる（分周比 1）。
フィルタでの減衰は −4.1dB → −7.3dB。T2/T3 を同じように比べて、よくなるかを見る。
よくなるならキャリアが原因（S1）で、段階 3 のソフト改修に進む。

```console
PICORUBY_PSG_PWM_DMA=0 R2P2_CONSOLE_UART=1 rake docker:r2p2:picoruby:pico2:debug
# 出力先は通常ビルドと同じ dist/picoruby-pico2-debug/ なので、比べるなら別名で退避しておく
```

※ DMA を使わない版はタイマー割り込みで 1 サンプルずつ書くので、別の問題
（割り込みの負荷、周期 45µs への切り捨てで約 22,222Hz）が出る可能性がある。比較用。

### 段階 3: ソフトを直す（原因が決まってから。直す前に方針を相談）

- **キャリアを上げる**: 比較値を 10bit（上限 1023）にし、1 サンプルを DMA で 6 回繰り返して書く。
  約 132kHz（−20dB 程度）になる。設計方針書の 10bit 案に揃う
- 折り返しを減らす: 帯域を制限した矩形波、または合成だけ高いレートで行う
- S4（パンが効いていない）、S5（分周比の切り捨て）、S7（ポップ）、S8（エンベロープ）は、
  音質の原因かどうかに関係なく直す価値がある

### 段階 4: ハードを測る・変える

- オシロで J3（生の PWM）、J6（フィルタ後）、スピーカー端子
- C22/C25 を 10nF にする（−3dB が約 6kHz まで下がり、音域の上が削れる。22.5kHz は約 −13dB）
- 別のスピーカーで比べる
- 5V を実験用電源から入れて、USB 電源のノイズを外す
