# 検証レポート — PIO で作った UART

2026-09-03、Raspberry Pi Pico 2 W 1 枚。設計は [plan.md](plan.md)。

**結論: PIO UART は動く。速度も足りる。基板 2 枚での確認だけが残っている。**

## 配線ゼロで検証できた

**TX と RX に同じピンを指定するとループバックになる。** PIO は自分が駆動している
パッドをそのまま読めるので、**ジャンパ線も 2 枚目の基板も要らない**。

```ruby
GroveLink.new(tx_pin: 15, rx_pin: 15, baudrate: 115_200)
```

GPIO15 を使ったのは、Pico 2 W で空いていてボードレイヤも使わないから。
**本番の GPIO28/29 は Pico 2 W では試せない**——GPIO29 は CYW43 のクロックで
ヘッダに出ていない（GPIO24＝SDB も同様に WL_D）。実基板は無線なしの RP2350A
なので問題ない。

## 機能

`devtest/pio_loopback.rb`:

```
got: "hello"           OK
then: "second" "third"          ← 続けて送った 2 行が両方届く
long: OK                        ← 20 バイト（FIFO 8 段より長い）
byte sweep: 0 wrong out of 127  ← 1〜127 の全バイトが往復
```

バイトスイープが通ったことで、**ビット順（LSB first）もフレーミング（8N1）も
サンプリング位置も正しい**と言える。

## 速度

`devtest/pio_throughput.rb`、115200:

| | 実測 |
|---|---|
| Ruby が FIFO を見に行く速さ | **76,400 回/秒**（1 回 13µs） |
| 115200 でのバイト間隔 | 87µs |
| スループット（73 バイトの往復） | **2,453 バイト/秒** |
| 一気に 32 バイト送って残った数 | **9** |

**FIFO の深さは速度を決めていない。** ポーリングは 13µs で済むのに、バイトは
87µs に 1 個しか来ないので **6.7 倍の余裕**がある。取りこぼす理由は
「見に行かないこと」だけで、FIFO が決めているのは**連続で受けられる塊の
大きさ**（8 バイト＋シフトレジスタ 1）。32 送って 9 残る、はその裏付け。

回線速度 11,500B/s に対して実測 2,453B/s なので、**律速は Ruby 側**。
ボタン 1 回が 2 バイトなので用途には 1,000 倍以上の余裕がある。
送る側がペースを作らないと 8 バイトで溢れる（`write` はそれをやっている）。
数十バイトのやり取りは下の節のとおり可能だが、**キロバイト単位を流すなら
ハードウェア UART の方が上**で、C 側にリングバッファがある
（`bytes_available` / `rx_overflow_count`）。

## 数十バイトは無理だった — そして DMA で解決した

PIO の FIFO は 8 バイトで、後ろに何も無い。**Ruby のポーリングでこれを守るのは
設計として成立していない**——GC が 1 回走るか、`matrix.show` の I2C が数 ms
伸びるだけで落ちる。しかも**黙って落ちる**（PIO に overflow フラグは無い）。

ポーリング版の測定では「8 バイトずつ送れば 20ms 空けても届く」という表が
作れたが、それはジッターの無い理想条件の話でしかなかった。
57 バイトのゲーム状態に 200〜300ms かかるのも、毎フレーム送る用途には論外。

### DMA で受ける

新しい gem [`mrbgems/picoruby-pio-uart`](../../mrbgems/picoruby-pio-uart/) を作った。
受信経路がプロセッサを一切通らない:

- ステートマシンが 1 バイトずつ DMA に渡す
- DMA が 512 バイトのリングに書く。**アドレスの折り返しはハードウェア**
  （`channel_config_set_ring`。バッファを自分のサイズ境界にアラインするだけ）
- **2 本目の DMA が転送カウンタを書き戻す**（`chain_to`）ので永久に止まらない

定石で、[dgatf/Pio-UART-RX-RP2040](https://github.com/dgatf/Pio-UART-RX-RP2040)
が分かりやすい実例。

### 結果

```
burst 200: 200 bytes, intact               ← Ruby は一切見ていない
after 500ms idle: 200 bytes, intact        ← 500ms 放置しても無傷
overran with 800: kept 512, overflow: true ← 黙って落とさず報告する
byte sweep 1..255: 0 wrong
write 200 bytes: 11,712 bytes/s            ← ほぼ回線速度（11,520）
```

ゲーム状態（57 バイト）:

```
state: intact              ← 送ってから 200ms 誰も読まなくても無傷
send took 4978us           ← 送信は 5ms
10 messages sent unread: 8 arrived, lost: true   ← 580 > 512 なので溢れ、報告される
```

**バッファ 512 バイトは、この 57 バイトの状態なら 9 フレームぶんの猶予**にあたる。
毎フレーム読むプログラムなら溜まりようがない。

残るコストは**送信が 5ms ブロックする**こと（C の中でループしている）。
33ms のフレームの 15%。必要なら送信も DMA 化できるが、失われるものは無いので後回し。

### 途中で踏んだ 2 つのバグ

**1. PIO のピン方向はステートマシン間で共有される。**
参照実装をまねて受信側で `pio_sm_set_consecutive_pindirs(..., false)` を
呼んだら、TX と RX が同じピンを指すループバックで**送信の出力が殺された**。
参照実装は別ピン前提だった。`pio_gpio_init` の後は既定で入力なので、この行は
そもそも要らない。

**2. RP2350 の `TRANS_COUNT` は上位 4 ビットが MODE。**

```
DMA_CH0_TRANS_COUNT_MODE_BITS          0xf0000000
DMA_CH0_TRANS_COUNT_MODE_VALUE_ENDLESS 0xf
DMA_CH0_TRANS_COUNT_COUNT_BITS         0x0fffffff
```

RP2040 では 32 ビット全部がカウントなので、**世の中の例はみな `0xffffffff` を
書く**。それを RP2350 に持ってくると **MODE=ENDLESS**（カウントを減らさずに
永久に走る）になり、**バッファは正しく埋まるのにカウンタが「0 バイト受信」と
言い続ける**。これで丸一往復デバッグした。`0x0fffffff` が MODE=NORMAL の
最大値で、この回線速度なら 6 時間半ぶん。

## 参考: ポーリングでどこまで行けたか

以下は DMA を入れる前、PIO の FIFO を Ruby でポーリングしていたときの測定。
**この方式は採用していない**が、FIFO の挙動の記録として残す。

**制限は速度ではなく「受信側が見に来るまでに何バイト載せたか」**で、
それが 8 を超えなければ落ちない。

57 バイトのゲーム状態風のメッセージを、送信の塊と受信のポーリング間隔を
振って通した（`devtest/pio_message.rb`。1 スレッドで送信側と受信側を交互に
演じている。2 枚の基板が直面する計算と同じ）。

| 送信の塊 | 受信ポーリング間隔 | 結果 | 所要 |
|---|---|---|---:|
| 4B | 2ms | OK | 56ms |
| 8B | 2ms | OK | 41ms |
| 8B | 20ms | OK | 197ms |
| **16B** | 20ms | **欠落** | — |
| 4B | 20ms | OK | 337ms |
| `write()`（自分でペースを作る） | — | OK | **22ms** |

**8 バイトを超える塊だけが落ちる。** 間隔は関係ない——20ms 空けようが、
8 バイトずつなら全部届く。FIFO の深さがそのまま規則になっている。

つまり 2 枚で数十バイトを送るときの条件は 1 つ:

> **受信側が次に見に来るまでに、送信側は 8 バイトを超えて載せない。**

`write` は 4 バイトごとに `pump` を挟むので、**送信側は約 1.6ms で 4 バイト**の
ペースになる。相手がそれに追いつくには **3ms に 1 回**は見に来る必要がある。
サンプルの `sleep_ms 20` のループのままでは足りない。

やり方は 2 つ:

- **受信側が頻繁に見る。** `pump` は 13µs なので、描画の合間に
  `10.times { link.pump; sleep_ms 2 }` のように挟めば足りる。
  57 バイトが 40ms 前後
- **送信側が遅くする。** 8 バイト送るごとに相手のループ周期だけ待つ。
  `sleep_ms 20` のループ相手なら 57 バイトで 200ms

ゲームの状態を毎フレーム送るなら前者、ときどき送るなら後者でよい。
**どちらも数十バイトには十分**で、届かないのは「8 バイトを超えて載せた」ときだけ。

### ポーリング版で測って直したこと

### 受信 FIFO が 4 ワードしかなかった

最初の実装では `"hello\n"` が届かなかった。6 バイトを一気に送って誰も読まなければ
溢れる。バイトスイープが通っていたのは 1 バイトずつ読んでいたから。

- **FIFO を寄せた。** TX と RX は別のステートマシンで、それぞれ使わない側の
  FIFO を持っている。`fifo_join: PIO::FIFO_JOIN_TX` / `..._RX` で 8 段
- **送信中も受信を吸うようにした。** `write` が `pump` を挟む

### Ruby 側が重かった（1,872 → 2,453 B/s）

- `@partial += char` が 1 バイトごとに新しい String を作っていた。
  行が長いほど二次的に遅くなる。`<<` の追記に変更
- `write` が 1 バイトずつ送り、`string[i]` が毎回 String を作っていた。
  4 バイトずつに変更（受信 FIFO 8 段の半分なら余裕がある）

### API を 2 組に分けた

`write` は送信しながら受信 FIFO を行バッファへ吸う。**行の API と生の API を
混ぜると、自分の送信が相手のバイトを食う。** バイトスイープが 1 件落ちて気づいた
（0 → 1 → 直して 0）。

| 組 | |
|---|---|
| 行 | `puts` / `write` / `gets` |
| 生 | `write_raw` / `read_byte` |

どちらかに寄せる。クラスのコメントにも書いた。

## メモリ

`lib/picorubykaigi01/grove_link.rb` は 5,870 バイト。

`examples/grove_link_chat.rb` は 4 本 require する（`picorubykaigi01` /
`led_matrix` / `buttons` / `grove_link`）。今のところ**一番重いサンプル**:

| | used | free | max_free |
|---|---:|---:|---:|
| 読み込み後 | 333,352 | 71,776 | 14,984 |

通る。実機では `matrix.clear` で `I2C write failed (IOError)` になるが、
これは LED ドライバの載っていない Pico 2 W なので**正しい失敗**。
コンパイルが通ってメモリに収まることは、これで確かめられている。
